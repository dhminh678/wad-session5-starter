## What I did not manage
While all 8 Done means rows, the empty mode, and the parallel stock request requirement are 100% satisfied across all three versions, several production considerations beyond the scope of this assignment were not implemented:
1. **Resilience to partial stock endpoint failures:** In versions A, B, and C, `Promise.all` uses fail-fast semantics; if a single `/api/stock/:id` returns 404 or 500, the entire stock calculation throws and fails. In production, using `Promise.allSettled()` would allow displaying the total for available items and gracefully logging missing items.
2. **Cancellation of stale in-flight requests on mode switch / retry:** If a user clicks Retry or changes test conditions while previous stock requests are still in flight, responses from the old fetch could theoretically resolve and mutate state. Introducing an `AbortController` to cancel pending requests when `load()` is re-invoked would eliminate this edge case.
3. **Client-side stock caching:** Each page load triggers 8 separate HTTP requests to `/api/stock/:id`. A production client would benefit from caching stock data in memory or relying on HTTP caching headers (`Cache-Control`, `ETag`) to avoid redundant network round-trips.

## What I would do differently
1. **Automate Done means testing upfront:** Writing a small Puppeteer / Playwright automation script at the start of the exercise significantly accelerated running all 5 conditions across all 3 versions and capturing exact network timings (e.g. measuring the 15 ms parallel request spread). I would set up this test runner before reading the versions.
2. **Consult native web platform specifications before accepting AI suggestions:** In Version B, recognizing that `{ timeout: 5000 }` was invalid in `RequestInit` was instantaneous once checked against MDN / WHATWG Fetch standards. Checking platform specifications directly prevents adopting third-party library conventions in vanilla browser code.
3. **Log interactions in real time:** Maintaining `AI-LOG.md` entries immediately after each prompt and fix captured genuine rejections and reasoning, avoiding the distortion of retrospective logging.
